## 1. 项目概述

一个基于 Spring Boot 3.2 的 WebSocket 即时通讯系统，支持用户注册/登录、好友管理、实时聊天、在线状态显示等功能。

**项目地址**：部署在腾讯云服务器，公网可访问

**关键词**：Spring Boot、WebSocket、JWT、Redis、MyBatis、MySQL、即时通讯

## 5. 认证系统

### 5.1 整体认证流程

```
┌─────────┐     ┌────────────┐     ┌──────────┐     ┌───────┐     ┌───────────┐
│ 浏览器   │ ──> │ login.html │ ──> │ /login   │ ──> │ Redis │ ──> │ HttpOnly  │
│         │     │ 输入用户名  │     │ API      │     │ 存token│     │ Cookie    │
│         │     │ 密码       │     │          │     │       │     │ 返回前端  │
└─────────┘     └────────────┘     └──────────┘     └───────┘     └───────────┘
                                                                            │
┌─────────┐     ┌────────────┐     ┌──────────┐     ┌───────┐              │
│ 浏览器   │ ──> │ /friendList│ ──> │ Jwt拦截器 │ ──> │ Redis │ <────────────┘
│ 自动带   │     │ 等API      │     │ 解析token │     │ 校验  │
│ Cookie   │     │           │     │ 查userId  │     │ token │
└─────────┘     └────────────┘     └──────────┘     └───────┘
```

### 5.2 为什么不用 Session？

| | Session | JWT |
|--|---------|-----|
| 存储位置 | 服务器内存 | 客户端 Cookie |
| 扩展性 | 多台服务器需共享 Session | 天然跨服务器 |
| 性能 | 查内存/共享存储 | 本地解析 token |
| 安全 | CSRF 风险 | XSS 防护需 HttpOnly |

### 5.3 为什么加 Redis？

**JWT 最大的问题**：一旦签发，服务端无法主动让 token 失效。

Redis 解决了这个问题：
```
登录：  生成 JWT → 存 Redis(key=token:user:3, value=JWT)
请求：  拦截器从 Cookie 取 token → 解析 JWT → 查 Redis 校验 → 通过
退出：  删 Redis 记录 → token 立即失效
管理员踢人：redis-cli DEL token:user:3 → 该用户下次请求被拦截
```

### 5.4 JwtUtil 详解

```java
public class JwtUtil {
    private static final String SECRET = "...";  // 签名密钥
    private static final long EXPIRATION = 24h;  // 过期时间

    // 生成 token（包含 userId + username）
    String generateToken(int userId, String username)

    // 解析 token（验签 + 解码）
    Claims parseToken(String token)

    // 取出 userId
    int getUserId(String token)
}
```

### 5.5 JwtInterceptor（HTTP 请求拦截器）

```
请求进来
    ↓
路径是 /login /register 或静态资源？──→ 直接放行
    ↓ 否
从 Cookie 中提取 token
    ↓
token 存在吗？  ──→ 不存在 → request.setAttribute("userId", null) → 放行
    ↓ 存在
解析 JWT
    ↓
查 Redis 校验 token 是否有效
    ↓
有效 → request 设置 userId, username → 放行给 Controller
无效 → request.setAttribute("userId", null) → 放行（由 Controller 判断）
```

### 5.6 JwtWebSocketInterceptor（WebSocket 握手拦截器）

WebSocket 握手时，浏览器自动携带 Cookie，拦截器从 Cookie 中取出 token：

```
WebSocket 连接请求（ws://host/WebSocketMessage）
    ↓
从 Cookie 提取 token
    ↓
解析 JWT
    ↓
查 Redis 校验
    ↓
通过 → attributes.put("user", user) → 握手成功
拒绝 → 握手失败，连接断开
```

### 5.7 HttpOnly Cookie 的作用

```
之前的方案（localStorage）：
localStorage['token'] = "eyJ..."   ← JS 可以读取！XSS 攻击下直接被偷

现在的方案（HttpOnly Cookie）：
Set-Cookie: token=eyJ...; HttpOnly  ← JS 无法读取！
浏览器自动在请求头携带 Cookie，开发者无感知
```

## 6. 在线状态系统

### 6.1 技术实现

Redis 的 Set 结构存储在线用户：
```
Key: "online_users"
Value: {"1", "2", "3"}  ← 在线用户的 ID
```

### 6.2 OnlineUserManger 组件

同时维护了**两份数据**：

```java
class OnlineUserManger {
    // 1. 内存（ConcurrentHashMap）—— 存 WebSocketSession，用于消息转发
    ConcurrentHashMap<Integer, WebSocketSession> sessions

    // 2. Redis（online_users Set）—— 存在线状态，用于好友列表显示
    StringRedisTemplate redisTemplate

    online(userId, session) {
        sessions.put(userId, session);          // 存 session
        redis.add("online_users", userId);       // Redis 记录在线
        通知所有好友：该用户上线了
    }

    offline(userId, session) {
        sessions.remove(userId);                 // 删 session
        redis.remove("online_users", userId);    // Redis 移除
        通知所有好友：该用户下线了
    }

    isOnline(userId) {
        redis.isMember("online_users", userId);  // 查 Redis
    }

    getSession(userId) {
        sessions.get(userId);                    // 查内存
    }
}
```

### 6.3 为什么用 Redis 存储在线状态？

| 方案 | 缺点 |
|------|------|
| 纯内存（ConcurrentHashMap） | **项目重启后在线状态丢失**，所有用户显示离线 |
| 存数据库 | 每次查询都要查 MySQL，太慢 |
| Redis | **项目重启后还在**，毫秒级查询 |

### 6.4 在线状态通知流程

```
用户 A 上线
    ↓
WebSocket 连接建立
    ↓
OnlineUserManger.online(A)
    ↓
查询 A 的好友列表
    ↓
向每个在线的好友发送：{"type": "online", "fromId": A}
    ↓
好友 B 的页面：将 A 的绿点亮起
```

## 7. WebSocket 即时通信

### 7.1 连接建立

```
浏览器：new WebSocket("ws://host/WebSocketMessage")
    ↓
服务器：JwtWebSocketInterceptor.beforeHandshake()
    ↓  Cookie 校验 JWT 通过
服务器：WebSocketAPI.afterConnectionEstablished()
    ↓
服务器：OnlineUserManger.online(userId, session)
    ↓
服务器：notifyFriends(user, true)  → 通知好友上线
    ↓
连接建立完成，可以收发消息
```

### 7.2 消息收发流程

```
用户 A 输入消息 "你好" → 点击发送
    ↓
前端：websocket.send(JSON字符串)
    ↓
{
  "type": "message",
  "sessionId": 1,
  "content": "你好"
}
    ↓
服务器 WebSocketAPI.handleTextMessage()
    ↓
1. 解析 JSON → MessageRequest
2. 调用 transferMessage(user, req)
    ↓
3. 构造 MessageResponse
   {
     "type": "message",
     "fromId": A的ID,
     "fromName": A的名字,
     "sessionId": 1,
     "content": "你好",
     "postTime": "2024-04-28 20:00:00"
   }
    ↓
4. 查数据库，获取该会话的所有用户
5. 遍历用户，通过 OnlineUserManger 获取 WebSocketSession
6. 给每个在线的用户发送消息
    ↓
7. 消息存入 MySQL（message 表）
```

### 7.3 断线处理

```
连接异常 / 关闭
    ↓
WebSocketAPI.handleTransportError() / afterConnectionClosed()
    ↓
OnlineUserManger.offline(userId, session)
    ↓
notifyFriends(user, false)  → 通知好友该用户下线
```

## 9. 全局异常处理与统一响应

### 9.1 统一响应格式 ApiResult<T>

```java
// 成功
ApiResult.success(data)
// → {"code": 200, "message": "success", "data": {...}}

// 成功（自定义消息）
ApiResult.success("注册成功", data)
// → {"code": 200, "message": "注册成功", "data": {...}}

// 错误
ApiResult.error(ResultCode.UNAUTHORIZED)
// → {"code": 401, "message": "未登录", "data": null}
```

### 9.2 ResultCode 枚举

| 枚举 | code | message |
|------|------|---------|
| SUCCESS | 200 | success |
| BAD_REQUEST | 400 | 请求参数错误 |
| UNAUTHORIZED | 401 | 未登录 |
| FORBIDDEN | 403 | 无权限 |
| DUPLICATE_USERNAME | 400 | 用户名已存在 |
| LOGIN_FAILED | 400 | 用户名或密码错误 |
| SERVER_ERROR | 500 | 服务器内部错误 |

### 9.3 GlobalExceptionHandler

```java
// 1. BusinessException → 返回 400 + 自定义消息
// 2. DuplicateKeyException → 返回 400 + "用户名已存在"
// 3. Exception → 返回 500 + "服务器内部错误"
// 4. 所有异常都打印日志
```

## 12. 完整用户流程

### 12.1 注册

**完整调用链：**

```
用户输入 username + password
  → 点击 register 按钮
  → register.html 第47行：submitButton.onclick()
  → $.ajax() POST /register
  → UserController.register()
  → UserServiceImpl.register()
      → BCrypt 加密密码
      → UserMapper.insert() 写入 MySQL（useGeneratedKeys 回填 userId）
  → 返回 User（含自增 userId）
  → 前端判断 body.data.userId > 0 → 跳转 /login.html
```

**各文件详解：**

**前端 register.html：**
- `document.querySelector('#submit')` 获取注册按钮
- `$.ajax({ url: '/register', type: 'post', data: { username, password } })` 发送请求
- `body.code === 200 && body.data && body.data.userId > 0` 判断注册成功

**后端 UserController.java → `/register` 接口：**
- 调 `userService.register(username, password)`
- `user.getUserId() <= 0` → 用户名重复，抛 BusinessException
- 成功 → 返回 `ApiResult.success("注册成功", user)`

**UserServiceImpl.java → `register()` 方法：**
- `User user = new User()` — 构造用户对象
- `user.setPassword(encoder.encode(password))` — BCrypt 加密，每次结果不同（含随机盐值）
- `userMapper.insert(user)` — `useGeneratedKeys=true`，自增 ID 回填到 `user.userId`
- `DuplicateKeyException` 捕获（username 有 UNIQUE 约束）→ `return new User()`（userId=0）

**UserMapper.xml：**
- `<insert id="insert" useGeneratedKeys="true" keyProperty="userId">`
- SQL：`insert into user (username, password) values (#{username}, #{password})`

### 12.2 登录

**完整调用链：**

```
用户输入 username + password
  → 点击 login 按钮
  → login.html 第40行：submitButton.onclick()
  → $.ajax({ url: '/login', type: 'post', contentType: 'application/x-www-form-urlencoded' })
  → UserController.login(username, password, HttpServletResponse)
      → UserServiceImpl.login()
          → userMapper.selectByName() — MySQL 查用户
          → encoder.matches(password, user.getPassword()) — BCrypt 验证
      → JwtUtil.generateToken(userId, username) — 生成 JWT
      → RedisTokenService.saveToken(userId, token) — 存入 Redis（24h）
      → Cookie("token", JWT).setHttpOnly(true).setPath("/").setMaxAge(24h)
      → response.addCookie(cookie)
  → 返回 User（userId > 0）
  → 前端跳转 /client.html（不需存 localStorage，Cookie 自动携带）
```

**各文件详解：**

**后端 UserController.java → `/login` 接口：**
- `userService.login(username, password)` — BCrypt 验证密码
- `jwtUtil.generateToken(userId, username)` — 生成 JWT
  - subject = userId，claim = username，iat = now，exp = 24h 后
  - HMAC-SHA384 签名，防篡改
- `redisTokenService.saveToken(userId, token)` — Redis key=`token:user:3`，24h 过期
- `Cookie cookie = new Cookie("token", token)` — 设置 HttpOnly Cookie
  - `setHttpOnly(true)` — 禁止 JS 读取 `document.cookie`
  - `setPath("/")` — 全站所有请求都携带
  - `setMaxAge(24*60*60)` — 24 小时过期
- 不再返回 token 给前端！前端完全不操作 token

**UserServiceImpl.java → `login()` 方法：**
- `userMapper.selectByName(username)` — MySQL 查询
- `encoder.matches(password, user.getPassword())` — BCrypt 明文 vs 密文
  - 从密文提取盐值 → 用盐值重算明文 → 比较结果
  - 失败返回 `new User()`（userId=0 表示失败）

**JwtUtil.java → `generateToken()`：**
```java
Jwts.builder()
    .subject(String.valueOf(userId))       // sub=3
    .claim("username", username)            // username=M
    .issuedAt(now)                          // iat=签发时间
    .expiration(new Date(now.getTime() + EXPIRATION))  // exp=24h后
    .signWith(SECRET_KEY)                   // HMAC-SHA384
    .compact()
```
生成结果示例：`eyJhbGciOiJIUzM4NCJ9.eyJzdWIiOiIzIn0.xxxx`（三段式 JWT）

**RedisTokenService.java → `saveToken()`：**
- key = `"token:user:" + userId`（如 `token:user:3`）
- value = JWT 字符串
- TTL = 24 小时（和 JWT 的 exp 一致）

### 12.4 WebSocket 连接建立

**完整调用链：**

```

  ↓ 浏览器自动携带 Cookie
JwtWebSocketInterceptor.beforeHandshake()  ← 第28行
  ↓ 从 Cookie[] 中提取 name="token" 的值
  ↓ jwtUtil.parseToken(token) — 解析 JWT
  ↓ redisTokenService.isValid(userId, token) — 查 Redis
  ↓ 通过 → attributes.put("user", user) → 握手成功
  ↓ 失败 → return false → 拒绝连接
WebSocketAPI.afterConnectionEstablished()  ← 第34行
  ↓ session.getAttributes().get("user") 取用户
  ↓
OnlineUserManger.online(userId, session)  ← 第21行
  ↓ sessions.put(userId, session) — ConcurrentHashMap 存 Session（消息转发用）
  ↓ redisTemplate.opsForSet().add(ONLINE_KEY, userId) — Redis 记录在线
  ↓ 如果已在线，先关闭旧连接
  ↓
notifyFriends(user, true)  ← 第94行
  ↓ friendMapper.selectFriendList(userId) — SQL 查好友
  ↓ 遍历好友 → onlineUserManger.getSession(friendId) 取 Session
  ↓ 在线 → session.sendMessage({"type":"online","fromId":3,"fromName":"M"})

**各文件详解：**

**JwtWebSocketInterceptor.java → beforeHandshake()：**

- `jwtUtil.parseToken(token)`：解析 JWT（失败抛异常 → return false）
- `redisTokenService.isValid(userId, token)`：Redis GET 校验
- `attributes.put("user", user)`：将 User 传入 WebSocketAPI

**WebSocketAPI.java → afterConnectionEstablished()：**
- `(User) session.getAttributes().get("user")` — 从握手阶段取用户
- `onlineUserManger.online(userId, session)` — 上线
- `notifyFriends(user, true)` — 通知好友

**OnlineUserManger.java → online()：**
- 双重存储：内存（ConcurrentHashMap）+ Redis（online_users Set）
- 旧连接处理：同一账号重复登录时关闭旧 WebSocket

public ApiResult<Void> logout(HttpServletRequest request, HttpServletResponse response) {
    Integer userId = (Integer) request.getAttribute("userId");
    if (userId != null) {
        redisTokenService.removeToken(userId);  // 删 Redis → token 失效
    }
    Cookie cookie = new Cookie("token", null);
    cookie.setHttpOnly(true);
    cookie.setPath("/");
    cookie.setMaxAge(0);  // MaxAge=0 → 浏览器立即删除
    response.addCookie(cookie);
    return ApiResult.success(null);
}
```

**RedisTokenService.java → removeToken()：**
- `redisTemplate.delete("token:user:3")` — 删掉后后续请求的 Redis 校验必失败

**OnlineUserManger.java → offline()：**
- `sessions.remove(userId)` — 删内存中的 WebSocketSession
- `redisTemplate.opsForSet().remove(ONLINE_KEY, String.valueOf(userId))` — 删 Redis 在线
- **重要**：只有同一个 session 才真正下线（防止误删）

### 12.10 服务端踢人（运维操作）

**管理员执行：**
```bash
redis-cli DEL token:user:3
# 或更狠：redis-cli FLUSHALL 清空所有 Redis 数据（所有用户 token + 在线状态全清）
```

**用户下次请求时的完整调用链（以点好友列表为例）：**

```
用户点"好友列表" → GET /friendList
  ↓ 浏览器自动带 Cookie（token 还在，JWT 本身未过期！）
JwtInterceptor.preHandle()  ← 第24行
  → extractTokenFromCookie(request) — 取到 token
  → jwtUtil.parseToken(token) — JWT 签名校验通过！因为 JWT 本身还没过24h
  → 解析出 userId=3
  → redisTokenService.isValid(3, token) ← 查 Redis！
      → Redis 中 token:user:3 已被管理员手动 DEL
      → isValid 返回 false！！！
  → request.setAttribute("userId", null)  ← 设置为未登录
  ↓
FriendController.getFriendList(request)
  → Integer userId = (Integer) request.getAttribute("userId");
  → userId == null → throw new BusinessException(401, "未登录");
  ↓
GlobalExceptionHandler.handleBusinessException()
  → 返回 ApiResult(code=401, message="未登录", data=null)
  ↓
前端 getUserInfo/getFriendList 等函数
  → body.code !== 200
  → alert('请先登录');
  → location.assign('/login.html');  ← 跳回登录页
```

**双重校验的核心代码 — JwtInterceptor.java 第 40-50 行：**
```java
try {
    Claims claims = jwtUtil.parseToken(token);           // 第一关：JWT 签名校验
    int userId = Integer.parseInt(claims.getSubject());   // 解析出 userId=3
    String username = claims.get("username", String.class);

    if (redisTokenService.isValid(userId, token)) {       // 第二关：Redis 存在性校验
        request.setAttribute("userId", userId);           // 两关都过 → 放行
        request.setAttribute("username", username);
    } else {
        request.setAttribute("userId", null);             // Redis 已删 → 不放行
    }
} catch (Exception e) {
    request.setAttribute("userId", null);                 // JWT 过期/被篡改 → 不放行
}
```

**这就是 JWT + Redis 双校验的核心价值：**

| 关卡 | 校验什么 | 防什么 |
|------|---------|-------|
| 第一关：JWT 签名 | 验签、过期时间 | token 被篡改、token 过期 |
| 第二关：Redis 存在性 | key=token:user:3 是否存在 | 退出登录、管理员踢人 |

两道锁都开了，才放行。

## 13. 面试话术

### 13.1 项目介绍

> "这是一个基于 Spring Boot 3.2 的 WebSocket 即时通讯系统，支持用户注册登录、好友管理、实时聊天、在线状态显示。后端采用 JWT + Redis 双校验实现无状态认证，通过 HttpOnly Cookie 防止 XSS 攻击。使用 WebSocket 实现消息的实时推送和在线状态通知，Redis 负责管理用户在线状态和 token，MySQL 做数据持久化。"

### 13.2 为什么用 JWT 不用 Session？

> "Session 方案在分布式部署时需要在多台服务器之间共享，复杂度较高。JWT 是无状态的，token 中直接包含用户信息，服务器只需验证签名即可，天然支持水平扩展。而且配合 HttpOnly Cookie，既能防止 XSS 窃取，又能让浏览器自动携带。"

### 13.3 为什么加 Redis？

> "JWT 有一个痛点：签发后服务端无法主动让 token 失效。引入 Redis 后，每次请求不仅校验 JWT 签名，还会查 Redis 验证 token 是否有效。这样退出登录、管理员踢人时，只需要删除 Redis 中的记录，token 立即失效。同时 Redis 也用来存储在线用户状态，项目重启后状态不会丢失。"

### 13.4 在线状态怎么实现的？

> "用户通过 WebSocket 连接成功时，将用户 ID 加入 Redis 的 Set 集合，同时向该用户的所有在线好友推送上线通知。断开连接时，从 Set 移除并推送下线通知。好友列表接口查询时，通过 Redis 的 SISMEMBER 判断每个好友是否在线，返回 online 字段。前端根据这个字段显示绿点或灰点。"

### 13.5 消息推送怎么实现的？

> "用户 A 发送消息后，WebSocket 处理器解析消息内容，查询数据库获取该会话的所有成员，遍历每个成员，通过在线用户管理器获取对应的 WebSocketSession，逐个推送消息。同时将消息异步写入 MySQL，用于历史消息查询和离线后重新上线时的消息同步。"

### 13.6 全局异常处理怎么设计的？

> "定义了一个 BusinessException 业务异常类，在 Controller 中遇到业务错误时直接抛出。GlobalExceptionHandler 使用 @RestControllerAdvice 统一捕获，将异常转换成统一的 ApiResult 格式返回。这样前端只需要根据 code 判断成功与否，message 显示给用户，data 解析业务数据，前后端契约非常清晰。"

## 14. 遇到的问题与解决方案

### 14.1 问题一：JWT 无法服务端撤销

**遇到的问题：**

一开始只用了 JWT，登录成功生成 token 返回前端，前端存 localStorage，每次请求带上 `Authorization: Bearer <token>` 头。用起来没问题，但仔细一想发现一个大坑：

```
用户退出登录 → 前端跳转登录页 → 但 token 还在有效期（24小时）！
用户手动构造一个请求 → 服务器验证 JWT 签名通过 → 操作成功！
```

这就意味着"退出登录"只是个摆设，**只要 token 没过期，任何人都可以拿着它冒充用户**。

**解决方案：引入 Redis 做 Token 校验**

```
登录：  生成 JWT → 存入 Redis → 设 HttpOnly Cookie
请求：  解析 JWT → 查 Redis 校验是否还存在 → 存在才放行
退出：  删 Redis 记录 → token 立即变成废纸
管理员踢人：redis-cli DEL token:user:3 → 3号用户被强制下线
```

这样 JWT 仍然是无状态的（服务器不存 Session），但通过 Redis 实现了**服务端可控**的效果。

### 14.2 问题二：JWT 存 localStorage 不安全

**遇到的问题：**

一开始 JWT 是存在浏览器 `localStorage` 里的，每次请求通过 JavaScript 读取然后设置 `Authorization` 请求头。这有一个严重的安全隐患：

```javascript
// localStorage 可以被任意 JS 读取！
localStorage.getItem('token')
```

如果网站存在 XSS 漏洞（比如用户在输入框写入恶意脚本），攻击者可以轻松窃取 token。

**解决方案：HttpOnly Cookie**

```
后端设置 Cookie：
  Cookie cookie = new Cookie("token", token);
  cookie.setHttpOnly(true);  // JS 无法读取！
  cookie.setPath("/");
  response.addCookie(cookie);

前端完全不需要操作 token：
  - 浏览器自动在请求中携带 Cookie
  - JS 代码中没有任何 token 相关的处理
  - 即使有 XSS 漏洞，攻击者也拿不到 token
```

HttpOnly Cookie 的核心原理：**浏览器禁止 JavaScript 通过 `document.cookie` 读取标记了 HttpOnly 的 Cookie**，但浏览器在发送 HTTP 请求时仍然会自动携带它。

### 14.3 问题三：Redis 操作很慢

**遇到的问题：**

加入 Redis 后，发现登录和退出操作要**转好几秒**才能完成，页面体验很差。一开始以为是 Redis 本身慢，但 `redis-cli ping` 响应是毫秒级的。

**诊断：**

Spring Boot 默认使用 Lettuce 作为 Redis 客户端。Lettuce 基于 Netty，默认**没有启用连接池**，每次操作都会创建新的 TCP 连接。

```
无连接池时：
请求 → 创建 TCP 连接（耗时 ~10-50ms）→ 操作 Redis → 关闭连接
下一个请求 → 又创建 TCP 连接（耗时 ~10-50ms）→ ...

每次操作都要经历 TCP 三次握手，大量时间花在建立连接上！
```

**解决方案：Lettuce 连接池**

加了 `commons-pool2` 依赖，并配置连接池参数：

```yaml
spring:
  data:
    redis:
      lettuce:
        pool:
          max-active: 8    # 最大连接数
          max-idle: 8      # 最大空闲连接
          min-idle: 2      # 最少保持 2 个空闲连接
          max-wait: -1ms   # 获取连接时无限等待
```

**连接池的原理：**

```
连接池初始化 → 预先创建 2 个连接到 Redis
请求来了 → 从池里借一个连接（< 1ms）→ 用完归还
请求多了 → 池自动扩容到最多 8 个连接
请求少了 → 慢慢缩容回 2 个空闲

避免了反复创建/销毁 TCP 连接的开销
```

**结果：** Redis 操作从几秒降到毫秒级，登录退出秒开。

### 14.4 问题四：前端页面加载慢，一直转圈

**遇到的问题：**

登录页面和聊天页面打开时**转圈很久**，有时候甚至加载不出来。F12 看 Network 发现是 jQuery 卡住了。

**原因：**

一开始使用 `bootcdn.net` 的 CDN 加载 jQuery：

```html
<script src="https://cdn.bootcdn.net/ajax/libs/jquery/3.6.0/jquery.min.js"></script>
```

`bootcdn.net` 在国内某些网络环境下访问极慢甚至超时。页面加载必须等 jQuery 下载完才能执行后续脚本，所以整个页面被阻塞。

**踩过的坑：**

第一次尝试把 jQuery 下载到本地，通过 WebFetch 获取内容后写入 `static/js/jquery.min.js`，但 WebFetch 有内容截断（只返回了部分内容），导致 jQuery 文件损坏。改成 `/js/jquery.min.js` 后控制台报错：

```
Uncaught ReferenceError: $ is not defined
```

**最终解决方案：**

换成更稳定的 CDN 源 `cdnjs`：

```html
<script src="https://cdnjs.cloudflare.com/ajax/libs/jquery/3.6.0/jquery.min.js"></script>
```

加上关了 HTTP/2（Spring Boot 3.x 默认开启 HTTP/2 和某些浏览器有兼容问题，导致请求异常）：

```yaml
server:
  http2:
    enabled: false
```

### 14.5 问题五：HTTP/2 协议错误

**遇到的问题：**

启动项目后，浏览器访问页面报错：

```
Failed to load resource: net::ERR_HTTP2_PROTOCOL_ERROR
```

页面刷新非常慢，有时候直接加载不出来。

**原因：**

Spring Boot 3.2 默认开启了 HTTP/2 支持。但 HTTP/2 需要 TLS（HTTPS）才能完整工作，在纯 HTTP 环境下，某些浏览器（特别是 Chrome）在协商协议时会出现异常。

**解决方案：**

```yaml
server:
  http2:
    enabled: false
```

关闭 HTTP/2 后，Tomcat 使用标准的 HTTP/1.1，兼容性最好，页面秒开。

### 14.6 问题六：数据库 password 字段太短

**遇到的问题：**

清空数据库后，尝试注册新用户，前端提示"服务器内部错误"，查看服务器日志：

```
Data truncation: Data too long for column 'password' at row 1
```

**原因：**

密码使用了 `BCryptPasswordEncoder` 加密，BCrypt 输出的字符串长度为 **60 位**。但旧数据库的 `password` 字段是 `VARCHAR(32)`，只能存 32 个字符，加密后的密码存不进去。

```
原始密码：123456
BCrypt加密后：$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
长度：60 位 > 32 位 → 截断报错！
```

**解决方案：**

```sql
ALTER TABLE java_chatroom.user MODIFY COLUMN password VARCHAR(128) NOT NULL;
```

把字段长度改为 128 位，足够存 BCrypt 的 60 位输出，也兼容未来可能的算法升级。

### 14.7 问题七：端口被占用无法启动

**遇到的问题：**

本地开发和服务器部署时都遇到过：

```
Web server failed to start. Port 8080 was already in use.
```

**原因：**

上一个项目的进程还活着，占着 8080 端口。

**解决方案：**

```bash
# 查看谁占用了 8080
netstat -ano | findstr :8080    # Windows
lsof -i:8080                     # Linux

# 杀掉进程
taskkill /F /PID <进程号>        # Windows
kill -9 <进程号>                  # Linux
```

**教训（服务器部署）：**

用 `nohup` 启动项目后，要检查进程是否真的起来了：

```bash
ps aux | grep java
```

如果起不来，看日志：

```bash
tail -100 app.log | grep ERROR
```

### 14.8 问题八：搜索结果包含自己和已加好友

**遇到的问题：**

搜索用户时，搜索结果显示了自己以及已经是好友的人。用户 A 搜索自己也能搜到，点"添加好友"没有任何反应。

**原因：**

原始的 `searchUser` 接口只是简单模糊查询：

```java
List<User> users = userMapper.selectByNameLike(username);
```

没有过滤掉当前用户和已经是好友的用户。

**解决方案：**

在 `UserServiceImpl.searchUser()` 中，查询到结果后，先获取当前用户的好友列表和自己的 ID，组成一个排除列表，然后过滤：

```java
List<User> users = userMapper.selectByNameLike(username);
List<Friend> friends = friendMapper.selectFriendList(currentUserId);

List<Integer> excludeIds = new ArrayList<>();
excludeIds.add(currentUserId);
for (Friend friend : friends) {
    excludeIds.add(friend.getFriendId());
}

List<User> result = new ArrayList<>();
for (User user : users) {
    if (!excludeIds.contains(user.getUserId())) {
        result.add(user);
    }
}
return result;
```

### 14.9 问题九：WebSocket 连接没有认证

**遇到的问题：**

最初的 WebSocket 连接**没有任何认证**，任何人都可以连接 WebSocket 并尝试收发消息。

**原因：**

WebSocket 握手时没有校验用户身份，`WebSocketAPI.afterConnectionEstablished()` 直接从 session 取 `user` 属性，但从来没设置过这个属性。

**解决方案：**

新增 `JwtWebSocketInterceptor`，在握手阶段从 Cookie 中取出 token，解析 JWT 并校验 Redis，通过后把 `User` 对象放入 session attributes：

```java
public boolean beforeHandshake(..., Map<String, Object> attributes) {
    String token = extractTokenFromCookie(request);
    Claims claims = jwtUtil.parseToken(token);
    // 校验 Redis
    if (!redisTokenService.isValid(userId, token)) {
        return false;  // 拒绝连接
    }
    attributes.put("user", user);  // 传给 WebSocketAPI
    return true;
}
```

### 14.10 问题十：服务器数据库密码字段不符

**遇到的问题：**

把新 jar 部署到腾讯云服务器后，注册时报错 "服务器内部错误"。排查后发现服务器上是旧的数据库，`password` 字段长度不够。

**原因：**

本地修改了数据库字段但没有同步到服务器。服务器上还是旧的表结构。

**解决方案：**

```bash
# 直接在服务器上执行
mysql -u root -p123456 -e "ALTER TABLE java_chatroom.user MODIFY COLUMN password VARCHAR(128) NOT NULL;"
```

**教训：** 涉及数据库结构变更时，一定要记得同步到生产环境，或者在代码中做兼容处理。更好的做法是使用数据库迁移工具（如 Flyway），但现在对于这个项目，手动执行 SQL 就够用了。
